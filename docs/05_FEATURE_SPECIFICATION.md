# 05 — Feature Specification

Each feature lists: ID, Name, User, Problem, Description, Preconditions, Main flow, Alternate flows, Error states, UI/Backend/DB/API requirements, Acceptance criteria, Priority, MVP/Post-MVP status.

---

## F-ONBOARDING — One-Time Farmer Profile Creation & WhatsApp Linking

- **User**: Farmer
- **Problem**: Farmers are tired of filling long government forms repeatedly every time they want to sell crops.
- **Description**: Farmer creates their profile once (Phone, Name, Village, District, Preferred Language, Aadhaar hint). Profile is permanently linked to their phone / WhatsApp number. Subsequent visits recognize the farmer immediately.
- **Preconditions**: Unregistered phone number.
- **Main flow**: Farmer enters phone → verifies OTP → inputs Name, Village, District, Language → Persistent profile saved in `farmers` & `users` tables.
- **Alternate flows**: Returning farmer logs in via phone/OTP or WhatsApp webhook directly → system recognizes existing profile and skips onboarding.
- **Error states**: Invalid OTP, network timeout.
- **UI**: Clean 3-step mobile card: (1) Phone & OTP, (2) Name & Village/District, (3) Language choice.
- **Backend**: `AuthService.verify_otp()` + `FarmerService.create_profile()`.
- **DB**: `users`, `farmers`.
- **API**: `POST /v1/auth/otp/verify`, `POST /v1/farmer/profile`.
- **Acceptance criteria**: Once completed, the farmer is never asked for their name, location, or identity details on subsequent procurement requests.
- **Priority**: P0 — MVP.

## F-PASS-GEN — Progressive & Conversational Procurement Pass Generation

- **User**: Farmer
- **Problem**: Booking a mandi slot shouldn't require filling a multi-page portal form when the system already knows who you are.
- **Description**: Farmer requests to sell a crop (e.g. *"I want to sell wheat"*). System retrieves their registered district, recommends nearby centres with live ETAs, asks **only** transaction-specific questions (Crop, Quantity in Quintals, Centre choice), and generates a digital procurement pass (`KQ-xxxx`) with a QR code.
- **Preconditions**: Farmer has completed one-time onboarding; selected centre is not PAUSED.
- **Main flow**: Farmer indicates crop ➔ Bot/App displays nearby centres with live congestion status & ETAs ➔ Asks *"How much wheat are you bringing?"* ➔ Farmer inputs quantity (e.g. 80 quintals) ➔ System displays transaction summary & estimated arrival window ➔ Farmer confirms ➔ System creates `queue_entries` and `qr_tokens` ➔ Issues Digital Pass (Token: `KQ-1047`) + signed QR.
- **Alternate flows**: Centre is PAUSED ➔ System shows delay reason and suggests alternative centres nearby.
- **Error states**: Quantity exceeds mandi daily limit; centre paused.
- **UI**: Conversational chat in WhatsApp or 1-screen quick booking card in Web App.
- **Backend**: `QueueService.generate_pass()`, `ETAEngine.compute()`, `QRService.issue()`.
- **DB**: `queue_entries`, `qr_tokens`.
- **API**: `POST /v1/queue/join` (or `POST /v1/passes/generate`).
- **Acceptance criteria**: Given a returning registered farmer, a digital pass is generated by answering only crop, quantity, and centre choice without re-entering identity details.
- **Priority**: P0 — MVP.

## F-CENTRE-STATUS — Centre Discovery & Live Status

- **User**: Farmer
- **Problem**: Farmer cannot see operational reality of a centre before traveling.
- **Description**: List/map of centres near the farmer's registered location showing operational status (Normal, Busy, Lifting Delayed, Reduced Capacity, Paused), queue length, and last-updated time.
- **Preconditions**: Location known from farmer profile or centre selector.
- **Main flow**: Farmer views centres sorted by distance/suitability ➔ sees color-coded operational status + estimated wait time.
- **Alternate flows**: Stale data (>30 min) flagged with yellow warning banner.
- **Error states**: Centre status unavailable ➔ explicit "Status unknown — please call centre" message.
- **UI**: Centre card with status badge, queue count, active counters, "Last updated Xm ago".
- **Backend**: `CentreService.get_status(centre_id)`.
- **DB**: `centres`, `capacity_updates`.
- **API**: `GET /v1/centres`, `GET /v1/centres/{id}/status`.
- **Acceptance criteria**: Displays accurate status badges and flags data older than 30 minutes as "Data may be outdated".
- **Priority**: P0 — MVP.

## F-QUEUE-LIVE — Real-Time Queue Position & ETA Tracking

- **User**: Farmer
- **Description**: Farmer tracks live queue position and ETA via WebSocket (Web) or on-demand WhatsApp query / push notifications.
- **Main flow**: Farmer opens "My Queue" or asks WhatsApp assistant ➔ sees position `#14 ➔ #13`, estimated wait in minutes, and confidence badge.
- **Alternate flows**: WebSocket disconnected ➔ fallback polling every 15s.
- **Error states**: Connection lost ➔ displays last known state with timestamp.
- **UI**: Animated position counter, ETA clock, confidence badge (High, Medium, Low), status banner.
- **Backend**: WebSocket Gateway (`/ws/{centre_id}`) + `ETAEngine`.
- **DB**: `queue_entries`.
- **API**: `GET /v1/queue/my-status`, WebSocket stream.
- **Acceptance criteria**: When officer updates centre capacity, farmer's ETA updates within ~2 seconds without page refresh.
- **Priority**: P0 — MVP.

## F-OFFICER-DASHBOARD — Officer Queue & Capacity Console

- **User**: Officer
- **Description**: Single-screen dashboard: today's queue list, 1-tap check-in, processing controls, and a 2-tap operational condition selector.
- **Main flow**: Officer logs in ➔ scans/enters token to check in arriving farmer ➔ marks processing started/completed ➔ updates status (Normal/Busy/Lifting delayed/Paused) when conditions change.
- **Alternate flows**: Manual token number fallback entry.
- **Error states**: Invalid / expired / already-scanned token.
- **UI**: Responsive table + prominent condition buttons with capacity % slider.
- **Backend**: `OfficerService`, `CapacityService`, `QueueService`.
- **DB**: `queue_entries`, `capacity_updates`, `processing_events`.
- **API**: `POST /v1/officer/checkin`, `POST /v1/officer/capacity`, `POST /v1/officer/queue/{id}/complete`.
- **Acceptance criteria**: Officer status update triggers background recalculation of all waiting ETAs and broadcasts WebSocket events immediately.
- **Priority**: P0 — MVP.

## F-QR-TOKEN — Digital Pass QR Issuance & Gate Validation

- **User**: Farmer, Officer
- **Description**: Generates HMAC-SHA256 signed QR code on digital pass. Officer scans QR at gate to check in farmer.
- **Preconditions**: Digital pass generated.
- **Main flow**: Farmer shows pass QR ➔ Officer camera scans QR ➔ Backend verifies signature & day-expiry ➔ Sets `is_used = TRUE` ➔ Moves entry to `CHECKED_IN`.
- **Error states**: Invalid signature, expired pass, already scanned, centre mismatch.
- **UI**: High-contrast QR code on farmer pass with large token string (e.g., `KQ-1047`).
- **Backend**: `QRService.issue()`, `QRService.validate()`.
- **DB**: `qr_tokens`.
- **API**: `GET /v1/qr/{queue_entry_id}`, `POST /v1/officer/checkin`.
- **Acceptance criteria**: Scanned QR verifies instantly; repeated scan of same QR is rejected with `ALREADY_CHECKED_IN`.
- **Priority**: P0 — MVP.

## F-WHATSAPP-ASSISTANT — Persistent WhatsApp Farmer Assistant

- **User**: Farmer
- **Description**: Persistent chatbot assistant recognizing returning farmers, assisting with centre recommendations, pass generation, ETA checks, and sending outbound delay alerts.
- **Preconditions**: Farmer phone linked during one-time onboarding.
- **Main flow**: Farmer messages *"I want to sell wheat"* ➔ Bot responds with recommended centres & live ETAs ➔ Asks quantity ➔ Farmer confirms ➔ Bot returns pass details and token.
- **Alternate flows**: Unlinked user ➔ Bot initiates 1-time onboarding prompts.
- **Acceptance criteria**: Simulates real conversation without repetitive identity questionnaires; queries hit real backend REST endpoints.
- **Priority**: P0 — MVP (in-app simulator) / Production integration P2.

## F-PROCUREMENT-PAYMENT — Post-Delivery Status Display

- **User**: Farmer
- **Description**: Post-weighing procurement receipt (weight, crop grade, MSP payout) and government DBT payment processing status.
- **Acceptance criteria**: Shows realistic delivery summary and pending/paid DBT transaction status (mocked via `GovernmentProcurementAdapter`).
- **Priority**: P0 (Procurement receipt) / P1 (Payment status) — MVP.

- **User**: Farmer, Officer
- **Description**: Full Hindi & English localization across Web and WhatsApp interfaces.
- **Acceptance criteria**: Zero English string leakage in farmer Hindi mode.
- **Priority**: P0 — MVP.
